# Актуальный аудит viewer_backend

Дата актуализации: 26 июля 2026 года.

## Назначение

`viewer_backend` хранит метаданные исследований и отчёты, принимает heartbeat
больничных агентов, управляет очередью `user_requests` и импортирует переданные
агентом CT/XA DICOM в удалённый PACS по HTTP.

## Реализованные маршруты

### Исследования

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/studies?page=1&page_size=10` | активные исследования с пагинацией |
| POST | `/studies` | создать протокол операции |
| DELETE | `/studies` | мягко удалить все исследования |
| GET | `/studies/search` | фильтрация по `study_date`, `surgeon`, `study_type` |
| GET | `/studies/patient/{patient}` | последнее исследование пациента |
| GET | `/studies/{study_id}` | исследование по внутреннему UUID |
| PATCH | `/studies/{study_id}/dicom-link` | обновить `dicom_link` |
| DELETE | `/studies/{study_id}` | мягко удалить исследование |
| POST | `/ct_studies` | принять CT, импортировать DICOM и создать запись |
| POST | `/xa_studies` | принять XA, импортировать DICOM и создать запись |

Singular-маршруты `/study...` пока сохранены только для обратной совместимости.
Новая документация и клиенты должны использовать `/studies...`.

`surgeon` и `study_type` обязательны, но не проверяются по фиксированным
справочникам.

### Отчёты

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | `/reports` | атомарно сохранить JSON-отчёт агента |
| GET | `/reports?limit=20` | получить последние отчёты |
| GET | `/reports/{filename}` | получить конкретный отчёт |

Каталог задаётся через `REPORTS_DIR`. В Compose используется постоянный volume
`reports-data`.

### Очередь агента

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | `/user_requests` | создать проверенную команду |
| GET | `/user_requests?agent_id=2` | атомарно забрать следующую команду |
| GET | `/user_requests/{request_id}` | получить статус и результат |
| POST | `/user_requests/{request_id}/result` | записать результат агента |

Поддержаны команды:

- `get_report`;
- `find_study`, `find_xa`, `find_ct`;
- `get_xa`, `get_ct`;
- `xa_polling_on`, `xa_polling_off`;
- `ct_polling_on`, `ct_polling_off`.

Имя команды принимается только из `command`. Статусы:
`pending → in_progress → completed|error`. Повторяемая ошибка временно возвращает
команду в `pending`; описание ошибки хранится и возвращается как `errors`.

PostgreSQL использует `FOR UPDATE SKIP LOCKED`, пятиминутный lease,
`attempt_count` и `max_attempts`. Повторная запись уже принятого terminal-результата
идемпотентна.

## Поток CT/XA

1. Агент выполняет прямой DICOM C-GET по `StudyInstanceUID`.
2. Агент строго проверяет число полученных и загруженных файлов.
3. DICOM загружаются в Yandex, backend получает `dicom_link` и временные URL.
4. Backend последовательно скачивает каждый файл, сверяет фактический размер,
   затем импортирует его в remote PACS.
5. Только после полного импорта backend создаёт запись CT/XA и отвечает успехом.
6. Агент хранит DICOM в Yandex трое суток и затем удаляет их по локальной очереди.

Повторный POST существующего сочетания `study_uid`/`modality` возвращает
существующую запись без повторного импорта.

Настройки backend:

```text
REMOTE_PACS_URL
REMOTE_PACS_USERNAME
REMOTE_PACS_PASSWORD
REMOTE_PACS_TIMEOUT_SECONDS
REPORTS_DIR
```

## Миграции

Историческая миграция `20260718000000_user_requests.sql` не изменялась.
Переименование статусов существующей очереди выполняет отдельная миграция
`20260726000000_user_request_statuses.sql`.

Перед запуском:

```bash
goose -dir internal/sql/migrations postgres "$DB_DSN" up
```

## Оставшиеся риски

### Критические для публикации

1. Backend не имеет аутентификации и разграничения ролей.
2. Любой клиент с сетевым доступом может читать медицинские данные и вызывать
   изменяющие endpoint’ы.
3. `DELETE /studies` массово скрывает записи без административного подтверждения.
4. Нет TLS/mTLS на уровне приложения; требуется защищённая сеть или reverse proxy.
5. `.env` ранее был добавлен в Git. Игнорирование файла не удаляет секреты из
   истории: реальные пароли необходимо ротировать отдельно.

### Надёжность и развитие

1. Нет OpenAPI и версионирования `/api/v1`.
2. Ответ списка исследований не содержит общего количества страниц.
3. Поиск пациента использует точное совпадение.
4. Нет уникального ограничения БД для CT/XA UID; идемпотентность сейчас
   обеспечивается проверкой приложения.
5. Нет метрик, tracing, request ID и отдельного readiness endpoint.
6. Нужны интеграционные тесты с реальными PostgreSQL, PACS и Yandex.

## Безопасная эксплуатация

- не публиковать `8080`, `8042` и `4242` в интернет;
- разрешать доступ только нужным узлам больничной сети/VPN;
- сменить тестовые пароли PostgreSQL и Orthanc;
- не передавать пароли или локальные пути через `user_requests`;
- выполнять резервное копирование PostgreSQL, Orthanc и `reports-data`;
- контролировать свободное место PACS и срок действия временных Yandex-ссылок.
