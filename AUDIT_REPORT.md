# Аудит viewer_backend

Дата аудита: 18 июля 2026 года.

## 1. Назначение приложения

`viewer_backend` — HTTP API на Go для серверной части DICOM viewer. Приложение не читает и не преобразует DICOM-файлы самостоятельно. Оно хранит метаданные исследований и ссылку `dicom_link`, по которой внешний viewer или PACS может получить данные.

Вторая задача API — принимать heartbeat/status-события агентов, отдавать их историю и управлять очередью команд `user_requests` для больничных компьютеров.

## 2. Что приложение умеет

### Исследования

- создавать запись исследования;
- выдавать список активных (не удалённых) исследований;
- применять пагинацию через `page` и `page_size`;
- искать исследование по UUID;
- получать последнее исследование пациента по точному совпадению имени;
- фильтровать список по дате, хирургу и типу исследования в любых комбинациях;
- обновлять только `dicom_link`;
- выполнять мягкое удаление одной или всех записей.

Мягкое удаление устанавливает `deleted = true`; данные остаются в PostgreSQL, но больше не возвращаются обычными запросами.

### Статусы агентов

- принимать статус агента `well` или `with_errors`;
- получать историю агента;
- получать историю агента с фильтром по статусу;
- физически удалять всю историю выбранного агента.

API сейчас принимает только `agent_id` 1 и 2. Время событий возвращается в однозначном формате RFC 3339.

### Очередь пользовательских запросов

Очередь поддерживает:

- постановку запроса в статусе `pending`;
- атомарный захват следующего запроса конкретным агентом через `FOR UPDATE SKIP LOCKED`;
- пятиминутную lease и повторный захват зависшего задания;
- явное подтверждение результата агентом;
- terminal failure и retryable failure с задержкой 30 секунд;
- ограничение числа попыток от 1 до 20;
- идемпотентное повторное подтверждение результата;
- просмотр состояния задания по UUID;
- поиск и удаление завершённых запросов старше трёх дней.

## 3. Архитектура и поток запроса

Приложение разделено на слои:

1. `cmd/main.go` загружает конфигурацию, проверяет PostgreSQL, собирает зависимости и запускает HTTP-сервер.
2. `transport/httpserver` разбирает HTTP-запросы и формирует ответы.
3. `transport/httpmodels` нормализует и валидирует входной JSON и query-параметры.
4. `services` задаёт прикладные операции. Сейчас этот слой в основном делегирует вызовы repository.
5. `repository/pgrepo` переводит доменные модели в параметры PostgreSQL и обратно.
6. `db` — код, автоматически сгенерированный `sqlc`.
7. `internal/sql` содержит schema, queries и миграции Goose.

Путь данных при создании исследования:

`POST /studies` → строгий JSON decode → валидация/нормализация → domain.Study → repository → sqlc → PostgreSQL → domain.Study → JSON response.

## 4. HTTP API после исправлений

### Основные REST-маршруты

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/` | простая проверка доступности процесса |
| GET | `/studies?page=1&page_size=10` | список исследований, `page_size` от 1 до 100 |
| POST | `/studies` | создать исследование |
| DELETE | `/studies` | мягко удалить все исследования |
| GET | `/studies/search` | поиск по `study_date`, `surgeon`, `study_type` |
| GET | `/studies/patient/{patient}` | последнее исследование пациента |
| GET | `/studies/{study_id}` | исследование по UUID |
| PATCH | `/studies/{study_id}/dicom-link` | обновить DICOM-ссылку |
| DELETE | `/studies/{study_id}` | мягко удалить исследование |
| POST | `/agent_status` | записать статус агента |
| DELETE | `/agent_status/{agent_id}` | удалить историю агента |
| GET | `/agent_status/searchby_id?agent_id=1` | история агента |
| GET | `/agent_status/searchby_status?agent_id=1&status=well` | история по агенту и статусу |
| POST | `/user_requests` | поставить проверенную команду агенту |
| GET | `/user_requests?agent_id=2` | атомарно получить следующую команду агента |
| GET | `/user_requests/{request_id}` | получить состояние и результат команды |
| POST | `/user_requests/{request_id}/result` | подтвердить успех, ошибку или повтор |

Старые singular-маршруты `/study...` сохранены для обратной совместимости.

### JSON создания исследования

```json
{
  "study_id": "STUDY-101",
  "patient": "Иванов И.И.",
  "age": 65,
  "department": "ОХМДиЛ",
  "name_operation": "Коронарная ангиография",
  "study_type": "каг",
  "descr_operation": "Плановое исследование",
  "time_beginning": "2026-07-17T10:31:00Z",
  "time_duration": 45,
  "surgeon": "идрисов",
  "dicom_link": "https://pacs.example/studies/STUDY-101"
}
```

Разрешённые хирурги: `идрисов`, `шпилевой`, `старков`, `киргизов`.

Разрешённые типы: `каг`, `цаг`, `стент_кор`, `стент_вса`, `стент_периферии`, `бап_кор`, `бап_вса`, `бап_периферии`, `тромбаспирация`.

## 5. Исправленные ошибки

### Критичные

- `study_type` отсутствовал в HTTP и domain моделях. В PostgreSQL записывалась пустая строка, а в ответе поле терялось.
- JSON-тег `time_begining` был написан с ошибкой. Корректное поле `time_beginning` из документированных запросов игнорировалось.
- параметры `limit` и `offset` вычислялись, но repository всегда возвращал полный список;
- HTTP 404 ошибочно отправлялся со статусом 400;
- `sql.Open` не проверял реальное подключение к PostgreSQL, поэтому процесс мог стартовать с недоступной БД;
- пул БД не закрывался, а лимит открытых соединений не задавался;
- таблица `user_requests` присутствовала в schema/sqlc, но отсутствовала в миграциях.
- очередь `user_requests` не имела HTTP/service/repository слоёв и не могла использоваться агентом;
- старый SQL захвата не разделял очереди по агентам и не использовал `SKIP LOCKED`;
- отсутствовали lease, ограничение попыток, JSON payload/result и идемпотентный callback.

### Валидация и API

- добавлена проверка обязательных полей исследования;
- запрещены отрицательные возраст и длительность;
- добавлена нормализация регистра/пробелов для хирурга, типа и статуса;
- валидируются допустимые хирурги, типы исследования, ID и статусы агентов;
- ID агента разбирается как `int32` без переполнения;
- JSON ограничен размером 1 MiB, неизвестные поля и несколько JSON-объектов отклоняются;
- создание ресурса возвращает HTTP 201;
- время статусов агента теперь возвращается как RFC 3339 вместо неоднозначного `HH:MM`;
- поиск пациента стал детерминированным: при нескольких записях выбирается последняя;
- добавлены REST-маршруты во множественном числе при сохранении старых маршрутов.

### Эксплуатация

- `HTTP_ADDR` имеет безопасное значение по умолчанию `:8080`;
- отсутствие `DB_DSN` обнаруживается до запуска сервера;
- подключение к БД имеет таймаут 5 секунд;
- настроены HTTP read/write/idle timeouts;
- исправлена сборка Makefile и устранены зашитые в target `run` реквизиты БД;
- добавлены `.env.example` и правило игнорирования `.env`;
- сгенерированный `sqlc`-код синхронизирован с SQL;
- добавлены unit/regression-тесты.

## 6. Проверки

Успешно выполнены:

- `sqlc generate`;
- `go test -race ./...`;
- `go vet ./...`;
- `go build -o /tmp/viewer_backend_audit ./cmd`;
- `make build`;
- `git diff --check`.

Дополнительно выполнен read-only smoke test с реальной локальной PostgreSQL на отдельном HTTP-порту:

- процесс успешно подключился к БД и запустился;
- `GET /` вернул 200;
- `GET /studies?page=1&page_size=2` вернул ровно две записи и корректные `study_type`/`time_beginning`;
- фильтр `GET /studies/search?study_type=каг` вернул ожидаемый JSON-массив;
- процесс корректно обработал сигнал завершения.

Записывающие и удаляющие интеграционные сценарии не запускались, чтобы не менять существующую локальную базу.

`goose status` подтвердил, что две старые миграции применены, а новая миграция `20260718000000_user_requests.sql` ожидает применения. Аудит не применял её автоматически.

После подключения hospital_agent дополнительно выполнен изолированный integration test во временном PostgreSQL-кластере в `/tmp`: миграции применились, команда прошла `pending → in_progress → completed`, повторный callback вернул тот же завершённый результат, а следующая выдача вернула пустую очередь. Рабочая локальная БД не изменялась.

`golangci-lint` в текущей локальной установке не работает с Go 1.24.3: установленная версия использует несовместимый type-checker. Это проблема версии инструмента, а не обнаруженная ошибка исходного кода.

## 7. Оставшиеся риски

### P0 — до любого production-развёртывания

1. В репозитории уже отслеживается `.env` с реквизитами PostgreSQL. Добавление в `.gitignore` не удаляет файл из истории. Нужно сменить пароль, удалить `.env` из индекса и при необходимости очистить Git history.
2. Нет аутентификации и авторизации. Любой клиент, имеющий сетевой доступ, может создавать, менять и удалять медицинские записи.
3. `DELETE /studies` массово скрывает все исследования без подтверждения или административной роли.
4. API обрабатывает персональные медицинские данные, но нет формальной модели доступа, аудита действий, шифрования/секрет-хранилища и политики хранения.
5. `DEBUG_ERRORS` нельзя включать в production: ответы могут раскрывать детали БД и внутренней реализации.

### P1 — надёжность и контракт API

1. Нет OpenAPI-спецификации и версионирования `/api/v1`.
2. Список исследований не возвращает `total`, `page`, `page_size`, поэтому UI не знает число страниц.
3. Фильтр и поиск пациента используют точное совпадение; нет полнотекстового/частичного поиска.
4. Списки допустимых хирургов и типов зашиты в код. Их лучше вынести в справочники БД.
5. Для `study_id` нет уникального ограничения или явно описанной политики дублей.
6. Нет database constraints для статусов, типов, положительных значений и ссылочной целостности.
7. Миграции не выполняются приложением и не включены в единый deployment workflow.
8. Нет интеграционных тестов repository/PostgreSQL и end-to-end теста реального HTTP-сервера.

### P2 — эксплуатация и развитие

1. Нет структурированных логов, request ID, метрик, tracing, readiness endpoint и наблюдаемости пула БД.
2. Нет Dockerfile/Compose и CI pipeline.
3. CORS не настроен; браузерный frontend на другом origin не сможет обращаться к API без reverse proxy.
4. `services` пока почти не содержит бизнес-логики, а repository зависит от конкретного `*db.Queries`, что усложняет unit-тесты.
5. Для очереди `user_requests` всё ещё нужен интеграционный конкурентный тест с реальной PostgreSQL.
6. Файл `init_db.sh` содержит фиксированные имя пользователя и пароль и рассчитан на Linux с `sudo -u postgres`.

## 8. Рекомендуемый план дальнейших действий

### Этап 1. Безопасность и стабильный контракт

- срочно ротировать опубликованные реквизиты;
- добавить JWT/OIDC или внутренний service-to-service механизм;
- ввести роли viewer/editor/admin и защитить delete-операции;
- отключить массовый DELETE либо перенести его в отдельный admin endpoint;
- описать OpenAPI 3.1 и зафиксировать `/api/v1`;
- согласовать единый формат ошибок и пагинированного ответа.

Критерий готовности: неавторизованный клиент не читает и не меняет данные; контракт проверяется тестами.

### Этап 2. Целостность данных и тестовая среда

- добавить миграцию с CHECK/UNIQUE constraints после анализа существующих данных;
- вынести типы исследований, хирургов и агентов в таблицы-справочники;
- поднять disposable PostgreSQL для integration-тестов;
- покрыть create/search/update/soft-delete и rollback миграций;
- добавить Docker Compose для локальной разработки.

Критерий готовности: CI создаёт чистую БД, применяет миграции и полностью проверяет API.

### Этап 3. Интеграция с viewer/PACS

- определить, что означает `dicom_link`: URL viewer, WADO-RS endpoint, StudyInstanceUID или локальный путь;
- хранить DICOM-идентификаторы отдельно от URL;
- добавить проверку доступности PACS и безопасную выдачу временных ссылок;
- не проксировать DICOM до определения требований к объёму, авторизации и кэшированию.

Критерий готовности: пользователь открывает выбранное исследование в viewer по стабильному и авторизованному сценарию.

### Этап 4. Очередь заданий и агенты

- добавить аутентификацию агента и административную авторизацию постановки команд;
- добавить список/фильтры очереди для admin UI;
- нагрузочно проверить `FOR UPDATE SKIP LOCKED` с несколькими агентами;
- добавить dead-letter состояние и метрики задержки;
- заменить фиксированные agent ID на реестр агентов.

Критерий готовности: несколько worker не обрабатывают одно задание одновременно, а зависшие задания наблюдаемы и восстанавливаются.

### Этап 5. Production-эксплуатация

- структурированные логи без персональных данных;
- request/correlation ID, Prometheus metrics и tracing;
- `/health/live` и `/health/ready`;
- CI/CD с проверкой миграций, тестами, lint и security scan;
- backup/restore drill и документированная политика хранения.

## 9. Следующий практический спринт

На ближайший спринт рационально взять:

1. ротацию секретов и удаление `.env` из Git;
2. OpenAPI `/api/v1`;
3. авторизацию и роли;
4. безопасную замену массового DELETE;
5. PostgreSQL integration tests в Docker;
6. пагинированный envelope с `total`;
7. CI на test/vet/lint/sqlc-diff.

Это закроет основные риски и создаст стабильную основу для интеграции frontend viewer и очереди агентов.
